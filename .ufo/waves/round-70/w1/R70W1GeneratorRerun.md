## 5. Advisory notes (non-blocking, no located defect)

- **A1 — the oracle digest is interpreter-pinned, not version-independent.** Under 3.13.16 the APK is identical
  but `truth.json` differs in exactly one line, `build_recipe.python_version` `3.14.8` → `3.13.16`, giving
  `d368b3309a06a9f370bd34626e9145270badb71ce15d724ce0f647313a861e5c` instead of `27303bae…`. The pin is
  therefore reproducible only under the recorded interpreter. Nothing in the candidate overclaims this
  (`truth.json` recipe text scopes determinism to "the recorded Python version"; `entry.md:209` scopes a digest to
  "exactly these bytes"), so this is not a defect — but a wave-2 seat re-running item 14 on a different `python3`
  will see a `truth.json` mismatch that is not a byte drift. If the author wants item 14 airtight, one clause
  naming the interpreter would close the gap; leaving it is defensible under the current wording.
- **A2 — DOS-time granularity can fake insensitivity in a mutation test.** `DOS_DATE_TIME` seconds are stored as
  `seconds/2` (ZIP spec), so a one-second perturbation is byte-invisible while a two-second perturbation moves the
  digest. Any future mutation seat probing this fixture must step the seconds field by ≥2 (or change date/hour) or
  it will wrongly conclude the digest is insensitive to the timestamp.
- No stale-byte finding: the working tree, the candidate commit `aa1842fa` and the claim base `3f5edbc2` all carry
  the same `generator.py`/`fixture.apk`/`truth.json` digests, so this evidence is not invalidated by a later
  wave-1 edit to those files (the candidate did not touch the fixture).
