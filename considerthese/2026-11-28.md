## New proposals (propose only, not acted on)

1. **Check PE export tables for forwarders and proxy-DLL patterns.** A DLL whose exports mostly forward to another DLL (for example `version.dll` exports pointing at `C:\\Windows\\System32\\version.orig`) is the classic DLL side-loading proxy shape. Record per DLL: export count, share of forwarded exports, forwarder targets, and whether the export names match a known system DLL of the same name. Flag a near-complete forwarded copy of a system DLL's exports plus a few real code exports as a strong side-loading signal, and treat it as weak evidence when forwarding is partial, since legitimate API-set and compatibility DLLs also forward.
2. **Read Mach-O load commands for platform, build bounds and signing.** LC_BUILD_VERSION (or the older LC_VERSION_MIN_*) gives the target platform, minimum OS and SDK version, which bounds the build date in the same way the 2026-11-27 ELF symbol-versioning proposal does. LC_CODE_SIGNATURE leads to the code directory, Team ID, ad-hoc vs. developer signing, and the embedded entitlements plist. Record all of these per slice (ties into the 2026-11-23 fat-binary proposal), and flag mismatches such as an SDK newer than the claimed build date or sensitive entitlements on an ad-hoc-signed binary.
